# GP-Planning 与 ROS 2 Nav2 集成笔记

本文分为现有 Python 方法、源码实现细节和后续 ROS 2 导航设想。第三部分是待验证的方案，不代表仓库已有机器人接口。

## 第一部分：现有 Python 实现

### 1.1 目标与范围

WELL-E 的目标是在有限移动时间内选择有信息价值的环境测量位置，并让机器人到达这些位置。现有 Python 仓库实现了候选节点、GP covariance、信息目标、pairwise travel-time matrix、GRG 路线，以及仿真中的测量与重规划。GRG 决定访问哪些 sensing nodes 及访问顺序；当前代码不生成机器人连续轨迹或底盘命令。

真实场地 Notebook 主要以 GCP 土壤含水量数据做实验。下文的 g(x,y) 表示通用空间环境场；温度测量是未来可用的场景，不应把当前实验表述为已完成的真实机器人温度采样。

### 1.2 候选 sensing nodes

候选节点在 GRG 运行前已经定义，GRG 只从中选择。合成实验使用归一化 5×5 网格 node_pts。真实场地使用 node_coords：node 0 是 VERNAL_BASE，node 1–30 是预定义 GCP，共 31 个 routing nodes。真实场地坐标来自 EPSG:32617 UTM，减去 GCP centroid 后仍以米计。

节点目前是二维位置 v_i=(x_i,y_i)。pool 边界的 detour waypoints 只是几何绕行辅助点，并非 sensing nodes，不在 GRG 输出的测量节点序列中。

### 1.3 GP、posterior covariance 与 MI

设环境场为 g(x,y)，观测为 y_i=g(z_i)+ε_i。GP kernel 在候选节点上形成 prior covariance matrix K_all；真实场地 Notebook 从训练后的 GP kernel 计算它。给定待测集合 A，posterior covariance 为：

$$
\Sigma_{V|A}=K_V-K_{VA}(K_{AA}+\sigma_n^2I)^{-1}K_{AV}.
$$

GRG 默认调用 gp_mutual_information()。若 X 为已经提交的节点，代码使用条件信息增益：

$$
I(y_A;f_V\mid y_X)
=
\tfrac12[\log\det\Sigma_{V|X}-\log\det\Sigma_{V|A\cup X}].
$$

MI 对测量节点集合评分，不依赖访问顺序；访问顺序决定行驶时间与可行性。K_all 描述节点间的信息相关性。

### 1.4 当前 travel-time model

GRG 接收 N×N 矩阵 tt，其中 tt[i,j] 是节点 i 到 j 的估计最短行驶时间，现有 Notebook 中单位是秒。合成网格以 Euclidean distance / speed 赋 edge weight。

真实场地模型利用已知 pool buffer：直线可通行时采用 direct distance / TRAVEL_SPEED；穿过 no-go zone 时，在 pool 边界外侧约 0.7 m 生成辅助 waypoint，建立 visibility graph，以最短绕行距离 / TRAVEL_SPEED 赋 edge weight。NetworkX 再计算 all-pairs shortest travel time。保存的真实场地运行结果：31 个 sensing nodes，148 条 direct edges、317 条 detour edges、0 个 infeasible pairs。当前 graph 无向，tt 对称；通用函数把不可达 pair 留为 inf，真实场地 Notebook 随后改为 9999.0。

**关键区别：这里的绕行是地图多边形与辅助点上的几何最短路径估算，不是机器人导航。** 例如 Notebook 05 中 node 0→6 的直线估计为 47.11 s，绕 pool 的 edge 与 `tt[0,6]` 均为 48.04 s：代码确实考虑了已知 pool，而非只用 Euclidean distance。但 `vis_G` 的点和线没有机器人 footprint、运动学、定位状态或控制反馈；`detour_vis_paths` 保存的是绘图用的绕行几何，不是 WELL-E 已执行的轨迹。`tt` 仍由几何距离除以固定 `TRAVEL_SPEED` 得出，不能证明机器人能沿这条线安全到达。

### 1.5 GRG 与输出

GRG 主要接收起终点 s、t、时间窗口、tt、K_all、noise_variance 和 depth。它近似寻找时间预算 τ 内信息量较高的路线 P：

$$
P^*\approx\arg\max_{P:s\rightarrow t}I(y_{A(P)};f_V),
\qquad
T(P)=\sum_{(i,j)\in P}tt[i,j]\leq\tau.
$$

grg_plan() 返回有序 node ID 列表或不可行时的 None。真实场地结果 [0,18,19,17,20,1,0] 表示从 base 出发访问五个 GCP 再返回。该列表不含连续轨迹、速度命令、MI 或实测行驶时间；后两项由调用方另算或留待未来执行。

### 1.6 仿真重规划

仓库既有一次性路线规划，也有 receding-horizon 仿真：

GRG 规划 → 取首个未访问节点 → 按 tt 模拟行驶 → 模拟测量 → 更新当前位置、已访问集合和剩余预算 → 再运行 GRG。

对应 Notebook 05 的 receding_horizon_grg_tour()、Notebook 06 的 rh_grg_generic() 和 Notebook 07 的 RH-GRG loop。测量值进入仿真评估用的 GP/measurement object；GRG 继续使用预计算 K_all，通过 _X_frozen、当前位置与剩余预算改变后续路线。这是仿真闭环，尚非真实机器人测量与导航。

### 1.7 哪些部分可沿用，哪些需要替换

本节首先评价 `GP-Planning` 原始 Notebook，尤其是 Notebook 05 的真实场地仿真。这里的“可沿用”表示已有明确的数据结构和算法接口，不代表预测精度、规划效果或实机部署已经验证。后续 `Code/10.18_Robot_close_loop_system` 的新增能力另行说明，不能把早期模型的限制直接套用于全部 Python 代码。

#### 1.7.1 可沿用的高层 informative planning

原始实现已经包含以下高层组件：

- 预定义的 candidate sensing nodes；
- GP covariance model 与候选节点上的 `K_all`；
- 默认 Mutual Information 及其他信息目标的实验接口；
- GRG 路线选择和 travel-time budget 判断；
- 有序 sensing-node ID 输出；
- 仿真中的 receding-horizon 重规划循环。

```text
候选测量节点 → GP / K_all → 信息目标 → GRG → 有序测量节点序列
```

**Interpretation：** 接入 ROS 2 时，可以保留这些高层职责与输入输出，优先替换移动成本和路线执行的数据来源。是否还需调整 GP、MI 或 GRG，应由预测与规划实验决定；保留接口不表示其性能无需改进。原始 Notebook 的 GRG 主要使用预计算 `K_all` 和已访问集合，具体更新方式见 1.6 与第二部分。

#### 1.7.2 关键限制：当前 pool 绕行是几何模型

Notebook 05 并非只用两点之间的直线距离。它根据已知 pool / no-go polygon 建立绕行模型：

```text
已知 pool 几何 → 在边界外生成辅助 waypoint → 建立 visibility graph
              → 求最短几何绕行距离 → 除以固定 TRAVEL_SPEED → tt[i,j]
```

$$
tt[i,j]=\frac{L_{ij}^{\mathrm{geometric}}}{\mathrm{TRAVEL\_SPEED}}.
$$

这能避免把穿过 pool 的直线当作可直接行驶的路线，但其判断仍基于点、线段和已知多边形。它回答的是“在这套几何模型中，绕过 pool 的最短距离与估计时间是多少”，不能据此确认真实 WELL-E 能完成该段导航。

辅助 waypoint 用于构造绕行路径，不是额外的 sensing nodes；GRG 仍然输出测量节点 ID。`detour_vis_paths` 记录的几何线也不等于机器人已经执行的轨迹。

#### 1.7.3 几何模型未覆盖的机器人因素

原始 pool visibility graph 未显式建模以下因素：

- ROS occupancy map / costmap，以及实际车体 footprint、宽度和长度；
- 机器人运动学、线速度和角速度限制、加减速与转弯过程；
- 动态障碍、定位误差和实际控制器行为；
- 实际导航成功、失败、超时，以及运行中路径被阻断后的恢复。

原始 Notebook 按 `tt` 累加行驶时间，随后更新当前位置并模拟测量，没有等待真实导航反馈。因此，**几何可行性 ≠ 实机导航可行性**。

**后续实验的范围更新：** `Code/10.18_Robot_close_loop_system` 已加入车体尺寸与安全余量对应的障碍膨胀、栅格 Dijkstra 路径、恒速移动模拟，以及导航/测量失败的高层处理。相关实现见 [navigation.py](../../Code/10.18_Robot_close_loop_system/testing_code/baseline/navigation.py)、[mission.py](../../Code/10.18_Robot_close_loop_system/testing_code/baseline/mission.py) 和 [failures.py](../../Code/10.18_Robot_close_loop_system/testing_code/baseline/failures.py)。这些是 Python 仿真与受控测试能力；[10.18 实验说明](../../Code/10.18_Robot_close_loop_system/README.md) 仍将真实导航、动态障碍恢复和实地采样列为待验证内容，不能表述为已完成 Nav2 或实机部署。

#### 1.7.4 第一条接口：替换 travel-cost matrix 的来源

原始 `grg_plan(..., tt, ...)` 已把 pairwise travel time 作为输入，因此移动成本的数据来源具有明确边界：

```text
原始实现：pool 几何 → visibility graph → 几何绕行距离 / 固定速度 → tt → GRG
后续方案：ROS 地图 / costmap + 机器人规划约束 → Nav2 路径 → 行驶时间估计 → tt_Nav2 → GRG
```

**Interpretation / 待验证方案：** 由外部导航系统提供与候选节点顺序一致的成本矩阵，可以保留 GRG 的高层角色。`tt_Nav2` 是方案名称，不是原始仓库已有变量。当前预算单位为秒，因此 Nav2 路径长度仍需转换为行驶时间估计，不能把米直接填入 `tt`。规划所得成本也不等于实测执行时间；具体约束、可达性与估计误差需要验证，详见 3.2。

#### 1.7.5 第二条接口：执行 GRG 选出的下一节点

原始 GRG 输出的是有序 sensing-node ID，例如 `P=[v0,v1,...,vn]`，不包含底盘控制命令。后续物理执行拟采用：

```text
GRG 下一节点 → 查找坐标并转换为 map-frame pose → Nav2 NavigateToPose
            → 导航结果及实际位置 / 时间反馈
            → 成功到达后取得有效实测 → 更新 GP / 已测状态 → GRG 重规划
```

**Interpretation / 待验证方案：** 导航失败或测量无效时，不把目标记为已成功测量，也不伪造读数；由实际状态与剩余预算决定后续规划。因此 Nav2 的两项主要职责是提供机器人规划条件下的路径成本估计，以及执行选出的目标并返回结果。候选 `(x,y)` 到完整 ROS `map`-frame pose 的变换仍需确定，详见 3.3–3.4。

#### 1.7.6 保留与替换的范围

| 部分 | 当前依据 | 后续处理（Interpretation） |
| --- | --- | --- |
| 候选节点、GP / `K_all`、信息目标、GRG、预算判断 | 原始实现具有明确接口，并输出有序 node ID。 | 保留高层职责，继续验证预测与规划效果；具体 GP 状态更新方式按所用实现确认。 |

### 2.1 GRG 主函数

主实现位于 `src/planners.py`，函数名为 `grg_plan()`，没有 GRG class。完整签名：

```python
def grg_plan(
    s: int,
    t: int,
    tau_start: float,
    tau_end: float,
    tt: np.ndarray,
    K_all: np.ndarray,
    noise_variance: float,
    depth: int,
    n_tau_splits: int = 5,
    _X_frozen=None,
    _mi_cache=None,
    objective_fn=None,
):
```

| 参数 | 当前含义 |
| --- | --- |
| `s`, `t` | 起点、终点的整数 node ID；真实场地往返路线通常以 `BASE_NODE=0` 为终点。 |
| `tau_start`, `tau_end` | 子问题的时间窗口；现有 Notebook 中单位为秒。 |
| `tt` | `n×n` 最短 pairwise travel-time matrix。 |
| `K_all` | 全部候选节点上的 `n×n` GP prior covariance matrix。 |
| `noise_variance` | GP observation noise variance。 |
| `depth` | 递归深度；`0` 只返回直接 `s→t` 路线。 |
| `n_tau_splits` | 对每个候选中间节点，在其可行时间窗口内尝试的 split-time 数量。 |
| `_X_frozen` | 已提交或已测量节点集合，用于条件信息目标。 |
| `_mi_cache` | 可选目标函数缓存，键为 `(frozenset(A), frozenset(X))`。 |
| `objective_fn` | 可选 `f(A_indices, K_all, noise_variance, X_indices) -> float`；默认为 `gp_mutual_information()`。 |

调用方分布：`notebooks/04_path_constrained_grg.ipynb` Cells 6、8、10、12、18、20、21、27–31；`notebooks/05_real_field_simulation.ipynb` Cells 26、28、32、44；`notebooks/06_temporal_nonstationary.ipynb` Cell 25；`notebooks/07_continuous_simulation.ipynb` Cell 24。没有 `.py` script 直接调用 `grg_plan()`。

递归会枚举中间节点 `v`，分别规划 `s→v` 与 `v→t`，将 `P1 + P2[1:]` 作为候选路线，并比较信息目标。当前代码中传入自定义 `objective_fn` 时，两个递归调用没有继续传递该参数；因此子问题使用默认 MI。这是代码现状。

`tt[i,j]` 是 NetworkX graph 中从节点 `i` 到 `j` 的最短 travel time。合成网格的 edge cost 为 `||p_i-p_j|| / speed`；真实场地对穿越 pool buffer 的节点对，使用 visibility graph 的绕行距离除以 `TRAVEL_SPEED`。`travel_time_matrix()` 对不可达节点对保留 `np.inf`；真实场地 Notebook 随后将其替换为 `9999.0`。保存的真实场地运行结果有 31 个节点、465 条 edge、0 个不可达节点。

`grg_plan()` 的预算为 `tau_end - tau_start`，当前 Notebook 中单位为秒。直接路径若 `tt[s,t] > budget + 1e-9`，返回 `None`；中间节点 `v` 只有在 `tau_start + tt[s,v] <= tau_end - tt[v,t] + 1e-9` 时才参与搜索。GRG 只返回 node ID 路线，坐标、路线时间、MI 和测量结果均由调用方另外取得。

### 2.2 节点与 graph

合成实验（Notebook 04 Cell 5）把 `NODE_GRID_SIZE=5` 输入 `np.linspace` 和 `np.meshgrid`，得到 `(25,2)` NumPy array `node_pts`，坐标范围是归一化 `[0,1]²`，单位为 field unit，不对应真实地图。例如 node 0、1、2、24 分别为 `[0,0]`、`[0.25,0]`、`[0.5,0]`、`[1,1]`；固定起终点 `s=0`、`t=24`。

`src/planners.py:build_complete_travel_graph(candidate_points: np.ndarray, speed: float) -> nx.Graph` 为每个数组行建立整数 node ID 和 `pos=(x,y)` 属性，并对每对节点建立无向 edge：

```python
dist = float(np.linalg.norm(candidate_points[i] - candidate_points[j]))
G.add_edge(i, j, weight=dist / speed)
```

Notebook 04 中 `speed=0.5` field-units/s，故 edge weight 和 `tt` 均为秒；保存输出 `tt[0,24]=2.828` 秒。这个 graph 是 complete。

真实场地（Notebook 05 Cell 15；Notebook 06/07 Cell 7）的节点变量是 `node_xc`、`node_yc`、`node_coords=np.column_stack([node_xc,node_yc])`，shape 为 `(31,2)`。node 0 是 `VERNAL_BASE`，node 1–30 对应按 `gcp_num` 排序的 `VERNAL_1` 至 `VERNAL_30`。坐标从 EPSG:32617 UTM Easting/Northing 减去 GCP centroid `cx,cy`，仍以米计；`node_abs` 保留绝对 UTM 坐标。保存值：`VERNAL_BASE=(587098.944,4790890.504)` m，`VERNAL_1=(587098.581,4790890.697)` m，centroid 约 `(587126.81,4790907.04)` m。

真实场地使用两个无向 NetworkX graph：`vis_G` 包含 sensing nodes 和 pool-buffer 外侧 waypoint，仅保留不穿过 `nogo_zone` 的 visibility edge；`G` 仅包含 31 个 sensing/base nodes。`G` 的 direct edge cost 是节点直线距离除以 `TRAVEL_SPEED=1.0` m/s；穿过 pool buffer 时使用 `vis_G` 的最短绕行距离除以该速度；绕行失败时不添加该 edge。保存输出：`vis_G` 有 83 nodes、960 edges；`G` 有 31 nodes、465/465 edges，148 direct、317 detour、0 infeasible。因此当前结果中的 sensing graph 是 complete，构造逻辑允许它在绕行失败时成为 sparse graph。

```python
if not seg_abs.crosses(nogo_zone):
    G.add_edge(i, j, weight=direct_dist / TRAVEL_SPEED, detour=False)
else:
    det_dist = nx.shortest_path_length(vis_G, i, j, weight='weight')
    G.add_edge(i, j, weight=det_dist / TRAVEL_SPEED, detour=True)
```

`src/planners.py:travel_time_matrix(G: nx.Graph) -> np.ndarray` 用 `nx.all_pairs_dijkstra_path_length(G, weight='weight')` 得到 `tt[i,j]`，即 graph 上最短路径的 edge weight 之和。初始未连通 pair 是 `np.inf`，真实场地 Notebook 随后将 `inf` 改为 `9999.0`，并把对角线置零。当前 graph 为无向且权重双向相同，故 `tt` 对称。使用它的 planner 有 `grg_plan()`、`nearest_neighbor_tour_fixed_end()`，Notebook 内的 myopic/RH planner 及路径时间评估也读取它。`scripts/vernal_pool_grid.py` 另生成 2 m 间距的 `grid_utm`、`grid_trav`，当前没有传给 GRG。

```python
T = np.full((n, n), np.inf)
for src, lengths in nx.all_pairs_dijkstra_path_length(G, weight='weight'):
    for dst, d in lengths.items():
        T[src, dst] = d
```

### 2.3 信息目标与 GP covariance

GRG 默认调用 `src/planners.py`：

```python
def gp_mutual_information(
    A_indices,
    K_all: np.ndarray,
    noise_variance: float,
    X_indices=None,
) -> float:
```

`A_indices` 为待测节点，`X_indices` 为已提交节点。该函数先对 ID 去重排序，因此目标依赖 unordered measurement set；route order 仅影响 travel cost 和 feasibility。公式为：

$$
I(y_A;f_V\mid y_X)=\tfrac12\left(\log\det\Sigma_{V|X}-\log\det\Sigma_{V|A\cup X}\right).
$$

代码中的 posterior covariance：

```python
K_cc = K_all[np.ix_(cond, cond)] + noise_variance * np.eye(len(cond))
K_vc = K_all[:, cond]
Sigma = K_all - K_vc @ np.linalg.solve(K_cc, K_vc.T)
```

Notebook 04 以 `src/solvers.py:rbf_covariance(a: np.ndarray, b: np.ndarray, lengthscale: float, outputscale: float) -> np.ndarray` 对 `node_pts` 建立 `K_all`。真实场地 Notebook 05 Cell 24 用训练后的 GPyTorch kernel 对 `node_coords` 建立 `(31,31)` 的 `K_all`，并传入标准化空间的 `NOISE_VAR`。`src/solvers.py:path_measurement_objective(ordered_indices, kernel: FixedKernel, candidate_points: np.ndarray) -> float` 是另一种顺序相关的 gain sum；其 docstring 说明它不是 GRG 的默认 MI。Notebook 06 Cell 25 另定义 `emse_obj(A_inds,K_all,nv_,X_idx)` 和 `wivr_obj(A_inds,K_all,nv_,X_idx)` 作为顶层 `objective_fn`，受 2.1 中的递归传参行为影响。

### 2.4 路线输出、预算与重规划

当前预算是 travel time（秒），不是距离或无量纲 cost。Notebook 05 用 base-to-GCP 往返 `tt` 校准出 `TIME_BUDGETS=[1.0,47.0,94.0,140.0]` 秒。Notebook 04 Cell 12 保存的实际结果：`path=[0,10,20,17,13,7,3,9,24]`、`path_time=7.45s`、`MI=14.5890`。其中 GRG 只返回 `path`；时间由 `sum(tt[path[i],path[i+1]])` 计算，MI 另由 `gp_mutual_information(set(path),...)` 计算。Notebook 05 Cell 28 在 `tau=47s` 时的路线为 `[0,18,19,17,20,1,0]`，访问 5 个不同的 GCP，MI 为 4.9282。

`grg_plan()` 的可行性检查在 `src/planners.py`：

```python
budget = tau_end - tau_start
if tt[s, t] > budget + 1e-9:
    return None
tau_lo = tau_start + tt[s, v]
tau_hi = tau_end - tt[v, t]
if tau_lo > tau_hi + 1e-9:
    continue
```

Notebook 04、Notebook 05 main sweep 和 Notebook 07 的 `grg_path_open` 是一次性规划完整路线。仓库也有 receding-horizon 仿真：Notebook 05 Cell 44 的 `receding_horizon_grg_tour(start, tt, K_all, noise_var, time_budget, depth=2, n_tau_splits=4, rng=None, max_replans=80)`；Notebook 06 Cell 25 的 `rh_grg_generic(start,tt,K,nv,budget,objective_fn,depth=2,n_tau=2,rng=None,max_rep=80)`；Notebook 07 Cell 24 的 RH-GRG loop（保存输出：10 次测量、11 次 replan）。

这些循环以当前节点、`remaining=budget-elapsed`、已访问集合 `_X_frozen` 重新调用 GRG；只执行返回路线中的首个未访问节点，按 `tt[current,nxt]` 累加时间，生成仿真测量，再重新规划。测量值进入仿真评估的 GP/measurement object；GRG 仍使用预计算的 `K_all`，路线变化由当前位置、剩余预算及已访问集合驱动。

```python
remaining = time_budget - elapsed
X_frozen  = frozenset(measured.keys()) | {start}
cache     = {}
plan = grg_plan(current, start, 0.0, remaining, tt, K_all, noise_var,
                depth=depth, n_tau_splits=n_tau_splits,
                _X_frozen=X_frozen, _mi_cache=cache)
if plan is None or len(plan) <= 1: break
next_nodes = [v for v in plan[1:] if v != start and v not in measured][:1]
if not next_nodes: break
nxt = next_nodes[0]
t_step = tt[current, nxt]
if elapsed + t_step + tt[nxt, start] > time_budget + 1e-9: break
elapsed += t_step;  current = nxt
measured[nxt] = simulate_measurement(nxt, rng)
path.append(nxt)
```

## 第三部分：计划如何使用 ROS 2 导航

本部分根据现有 Python 接口和后续讨论整理，均为 **Interpretation / 待验证方案**。尚未实施，也不表示 WELL-E 目前已具备下列 ROS 2 组件。

### 3.1 分工与现有模型的限制

GP、MI、GRG 保持高层 informative planning：决定“去哪测、按什么顺序测”。拟由 ROS 2/Nav2 承担物理导航：决定“如何到达”，并反馈是否真的到达。

当前 real-field travel model 已能在已知 pool buffer 周围寻找几何绕行，但仍假设静态几何、近似点状机器人、固定速度与成功行驶。它不能单独回答 WELL-E 在实际 footprint、驱动方式、速度限制、定位误差或现场障碍下能否完成某段行程。**关键替换有两层：让物理导航提供可达性与行驶成本，再实际执行 GRG 选出的下一节点并反馈结果。**

### 3.2 用外部规划结果提供 `tt`

**拟对接点：** `grg_plan(..., tt, ...)`。GRG 根据 `tt` 判断时间可行性，并不要求矩阵由哪一种规划器产生。现阶段先保留 GP、`K_all`、MI 和 GRG 的输入输出，用 Nav2 规划得到的物理路径估计 pairwise travel time。两条数据链的区别是：

```text
当前：sensing nodes + 已知 pool 多边形
      → 几何辅助点 / visibility graph → 距离 ÷ 固定速度 → tt_geo → GRG

拟议：sensing nodes → map-frame poses + 机器人地图/约束
      → Nav2 规划的可行路径 → 估计行驶秒数 → tt_Nav2 → GRG
```

图中的 `tt_geo` 是对现有几何成本的说明性名称，源码变量实际叫 `tt`；`tt_Nav2` 是未来方案，仓库中尚不存在。二者扮演相同的 GRG 输入角色，但来源不同。前者只检查线段是否穿过已知 pool 并计算多边形绕行；后者需要机器人可用的地图、定位及规划配置。即使获得 `tt_Nav2`，还要执行导航并接收成功/失败反馈；成本矩阵本身不会驱动机器人移动。

对 sensing nodes `i,j`，先要有 ROS `map` frame 中的目标 pose：

$$
q_i=(x_i^{map},y_i^{map},\theta_i),\qquad
q_j=(x_j^{map},y_j^{map},\theta_j).
$$

若外部规划器对 `q_i→q_j` 给出路径 `\pi_{ij}=[p_0,\ldots,p_m]`，可计算路径长度：

$$
L_{ij}=\sum_{k=0}^{m-1}\|p_{k+1}-p_k\|.
$$

第一版可用 `tt_Nav2[i,j]≈L_ij/v_nominal` 估计秒数，与当前以秒计的 `τ` 保持一致。这个估计仍不等于真实执行时间；控制、加减速、转向和停障的影响需要后续验证。若规划器未给出有效路线，可暂将对应 pair 标为不可达并重新检查 GRG 可行性。pose 中包含方向时，`i→j` 与 `j→i` 的代价可能不同，不能沿用当前无向 graph 的对称性假设。

原文曾建议直接用 `L_ij` 作为 GRG cost；若仍采用秒为单位的 `τ`，不能把米直接填入 `tt`。若将预算也整体改成米，那是另一种明确的实验设定。

### 3.3 GRG node ID 到实际导航目标

GRG 返回 `[v_0,v_1,v_2,...]`。拟沿用现有 receding-horizon 方式，每次只取下一个未访问 sensing node，而不是把整个列表当作已可执行的机器人轨迹：

`next node ID → node_coords / node_abs → map-frame pose → PoseStamped goal → Nav2 navigation`

`node_coords` 是 centered UTM 米坐标，`node_abs` 是绝对 UTM 坐标；两者目前都不是 ROS `map` frame pose。还需要确定 UTM/field 与 `map` 的坐标关系，以及每个 sensing goal 的方向 `θ_i`。仓库没有该变换，也没有节点朝向策略。

### 3.4 导航反馈、测量与重规划

现有 Notebook 在选出 `nxt` 后直接累加 `tt[current,nxt]`、更新 `current` 并模拟测量。未来的外部执行结果应在这些状态更新之前进入：

| 外部结果 | 拟采取的高层处理 |
| --- | --- |
| 到达成功 | 更新实际已用时间与当前位置；读取真实传感器；记录测量和已访问节点；以剩余预算再次运行 GRG。 |
| 失败、超时或无法到达 | 不把目标记为已访问，不伪造测量；根据实际情况更新可达性或成本，再规划。 |

这是拟议的状态流，不是仓库现有的回调。真实测量如何更新 GP posterior、是否重估 kernel 参数，以及导航失败如何修改 pairwise cost，仍需后续确定。当前模拟的 GRG 已利用 `_X_frozen` 条件化已访问集合，但保持预计算的 `K_all`。
